# Complaint concurrency evidence and design

Old/current canonical AddProcessing and UpdateStatus both INSERT into the same processing table. Neither allocates an identity while holding a parent write lock. The old trigger directly assigns from its own INSERTED rows. Rank within INSERTED fixes batches but cannot preserve max committed identity when identity allocation and trigger completion orders differ.

`before-concurrency.json` uses two real SQL sessions running canonical stored procedures, plus a disposable gate on an unrelated existing complaint. A test-only hook pauses the smaller identity after insertion, before status synchronization. The other writer allocates a larger identity and commits first. After releasing the gate, both calls commit but the old trigger assigns the smaller row's status; both CSKH-first and Admin-first probes record mismatch=true against persisted max XuLyID. `before-probe.json` separately records four ordinary batches whose current execution plan happened to return the right status; no batch mismatch is invented.

The current trigger first obtains U/HOLD locks on distinct affected parent rows in a separate statement without emitting a recordset. This barrier precedes the authoritative history query. It then ranks all processing history for affected complaint IDs by XuLyID DESC and joins rn=1 to the parent update. Reading only INSERTED, ranking by timestamp, or relying on the parent UPDATE to acquire its lock after a precomputed history snapshot would not provide the same guarantee.

`complaint-concurrency.json` repeats both delayed smaller-identity schedules: high identity commits first, smaller identity completes afterward, both persist, parent still equals the high identity's status. It also runs eight canonical held-caller cases (CSKH/Admin × AddProcessing/UpdateStatus × first commit/rollback) and two overlapping mixed-batch cases. Actual DMV waits include KHIEUNAI/XULY_KHIEUNAI lock resources/indexes; final data and clean sessions are recorded.

READ_COMMITTED_SNAPSHOT remains ON. Each history SELECT is a new READ COMMITTED statement after the parent barrier; own uncommitted processing rows and already committed competing rows are visible. No NOLOCK, child SERIALIZABLE range lock, new lock table/index, or Node transaction is added. The existing role trigger remains active and unchanged; FK/CHECK/rollback guards remain authoritative.

Multiple-parent inserts can still contend, including FK checks and parent lock conversions. No general deadlock-free claim is made. A deadlock victim, if encountered in an alternate schedule, must roll back its statement/transaction; acceptance is based on latest persisted committed history and no partial parent/child state. The tested schedules record actual outcomes rather than silently retrying failures. Explicit SNAPSHOT transactions/ad-hoc privileged UPDATE/DELETE of history are outside the canonical READ COMMITTED append-only runtime contract; the trigger's event remains AFTER INSERT.
